## 0. 这份文档怎么用

### 0.1 定位：与 playbook 的关系

Anthropic 的《The AI-native SDLC playbook》回答的是：**流程长什么样**——六个阶段、十二个 play、一条 Git 产物链。

这份手册回答的是它没有正面回答的问题：**这样的流程跑起来之后，人类看不懂产物、不敢签字、无法论证，怎么办。**

一句话分工：

> **Playbook 管骨架，本手册管信任。**
>
> 用 playbook 的六阶段和产物链做流程骨架，用本手册的六条机制、变更分级和理解审计，保证每个产物都有人能真正负责。

本手册不是 playbook 的替代品，也不复述它。两者应当配合使用，对照关系见第 3 章。

### 0.2 使用方式

- 负责人先通读第 1~4 章，理解原则。
- 开工时照着第 5 章（首版）或第 6 章（迭代）执行。
- 日常对照第 7 章速查表。
- 落地节奏参考第 9 章。
- 附录 A~F 是可直接抄用的模板与术语表。

### 0.3 硬规则

> 可以省流程、省签字，但**契约、证据、范围守卫**一条都不能省。那是唯一的信任来源。

## 1. 问题诊断

按 AI Native 方法开发的项目，典型症状是：过程产物（代码、文档、报告）人类看不懂，最终功能能跑但夹杂着没人要的东西，所以没人能签"我担保它是对的"。

这不是"文档写得不够"。这是三件事同时发生：

### 1.1 生成速度 > 审查带宽

AI 一天产出的 diff 超过团队一周能读完的量，review 退化成橡皮图章——"看起来没问题"。

Playbook 自己也承认这个转移：Agent 把 Build 压到几小时，瓶颈落到人速的 Plan、Design、Review、Deploy。但它没有解决"人速环节到底该做什么判断"。

### 1.2 意图与实现断链

人给的是意图，AI 给的是实现，中间那层"为什么这么选"的决策记录不存在。出了问题只能看到"代码这么写"，无法论证"这么写对不对"。

`intent.md` 解决了"意图有没有被记录"，但没有解决"关键决策有没有被人类判断"。一份写得很长的 intent 也可能没人真正读过。

### 1.3 自洽但错误的验证

AI 写的实现配 AI 写的测试，两者共享同一套错误假设，测试全绿但语义是错的。这是最危险的一类，因为它伪装成"已验证"。

`verifier subagent` 能缓解，但**验证者与实现者如果共享同一套 spec 假设，仍然会一起错**。所以本手册要求独立证据和人类可确认的来源。

### 1.4 为什么文档和报告也看不懂

因为 AI 写文档的默认行为是**描述实现**，而不是**记录决策**。描述实现的文档和代码一样不可读，还更容易过期。有价值的文档只记录：决策、理由、约束、风险。

## 2. 核心判断

软件工程里的信任，从来不是靠"人读完了全部代码"。

波音没人读得懂全部设计，芯片没人看得懂全部网表，但它们可信——靠的是**契约 + 独立证据 + 可逆性**，不是靠"理解"。

### 2.1 两条路，必须同时走

- **路 A：让人重新获得理解** —— 缩小步长、限制自由度、收敛技术栈，把产物压回人类可读的复杂度。
- **路 B：让人不必理解也能负责** —— 用契约、独立验证、爆炸半径控制和可逆性，把"看不懂"变成**有界风险**。

只走路 A，规模上不去；只走路 B，风险失控。

### 2.2 三种产物

每个阶段只允许三种产物存在：

| 产物 | 谁产出 | 作用 |
|---|---|---|
| **契约** | 人定、人签字（AI 只能辅助起草） | 意图、验收标准、接口、边界、依赖白名单 |
| **实现** | AI 写 | 可丢弃、可重写的代码 |
| **证据** | 机器独立产出 | 测试、指标、扫描报告、灰度数据 |

### 2.3 一条纪律

> **契约由人定，实现由 AI 写，证据必须独立于实现。**

人的时间只花在契约和证据上，不试图读懂全部实现。

### 2.4 一个判断标准

信任不来自"人类读懂了 AI 的代码"，而来自"**人类能对 AI 的行为做出可辩护的判断**"。前者在规模下是幻觉，后者才是工程。

## 3. 与 Anthropic《The AI-native SDLC playbook》的对照

> 来源说明：Anthropic 原文发布于 claude.com（文章版）与 Claude Academy（课程版），约 2026-08-21，Applied AI 团队（二手来源记为 Louis Claxton）。本节依据检索到的原文转述与第三方摘要整理；个别细节（如 play 的确切数量与命名）二手来源存在出入（12 与 16 两种说法，以原文为准）。

### 3.1 它是什么

核心论点一句话：

> **"Code is no longer the bottleneck. Your SDLC is."**
>
> 代码不再是瓶颈，你的软件开发生命周期才是。

Agent 把 Build 阶段压缩到几小时，约束就转移到了围在代码周围的人类环节——Plan、Design、Review/Test、Deploy。所以 playbook 不是在教"怎么让 AI 写更多代码"，而是在**重新设计人速环节**。

### 3.2 六阶段与产物链

```
Plan → Design → Build → Test → Deploy → Maintain
  ↑                                        │
  └────────── 新的 intent.md ←─────────────┘
```

每个阶段结束时，必须向 Git 提交一个产物，下一个阶段读它：

| 阶段 | 产物 | 谁负责 | 本手册对应 |
|---|---|---|---|
| **Plan** | `intent.md` | 产品负责人写并批准，不是工程师 | 变更意图卡 / 附录 A |
| **Design** | `spec.md` | Claude 在组织 skills 约束下生成，PO 审阅但不撰写 | 附录 A 的验收标准部分 |
| **Build** | `plan.md` + diff | plan mode 出计划，人批准后才写代码 | 第 5.4 节的切片流程 |
| **Test** | tests + evals | 先写失败测试；verifier subagent 独立验证 | 第 4.3 节 + 5.5 节 |
| **Deploy** | PR + review findings | agentic PR review，人工审查留给关键代码；approval hooks 把门 | 第 6.2 节 L2/L3 |
| **Maintain** | incident record → 新的 `intent.md` | 确定性控制带检测，模型不参与检测；越界诊断写回 Plan | 第 5.4 节持续机制 |

**关键设计**：生命周期是环，不是线。Maintain 发现的异常不是"打个补丁"，而是变成一份新的 `intent.md` 重新进入 Plan，走完整的意图 → 规格 → 计划 → 验证链条。

### 3.3 按阶段归并的 play 清单与本手册映射

> play 名称为二手转述的机制归并，以原文为准。

| 阶段 | Play / 机制 | 它解决什么 | 本手册的对齐点 | 本手册的补充 |
|---|---|---|---|---|
| **Plan** | `intent.md`：问题、预期结果、受影响用户/系统、约束、开放问题 | 意图可追溯 | 变更意图卡 | 要求列出**关键决策**和**不做什么** |
| **Design** | 组织 standards（品牌、安全、合规、UX）编码为 **skills**，Claude 生成 `spec.md` | 设计约束可复用 | CLAUDE.md 项目宪法 | 要求每条验收标准对应**可观测证据**，不接受散文式 spec |
| **Build** | **plan mode 默认**："no approved plan, no implementation" | 防止跳过设计直接写 | 第 5.4 节第 2 步 | 计划里必须包含**关键决策与备选**，不只是"改哪些文件" |
| **Build** | **CLAUDE.md 作为团队记忆**；同一个错误犯两次，就把纠正写进去 | 约束固化，减少重复犯错 | 附录 B | 增加**依赖白名单**与**禁止事项** |
| **Build** | **skills 作为组织知识** | 让 AI 产出符合组织范式 | 4.6 约束优于审查 | 强调可读性来自**一致性**，不来自漂亮 |
| **Build** | **hooks 作为确定性护栏**（"skill 让违规变罕见，hook 让违规几乎不可能"） | 概率性约束 → 确定性约束 | 4.6 + hooks | 明确哪些是 must-hold、必须上 hook |
| **Build** | **并行 session / subagent**，起步 2~3 个，上限由**审查能力**决定 | 提升产出 | 6.3 度量换成审查带宽 | 并行数不是产能指标，**审查带宽才是天花板** |
| **Test** | **先写失败测试**；修复时用 hook 禁止改测试 | 防止"改测试让它通过" | 4.3 独立验证 | 测试来源必须是**人类可确认的现象** |
| **Test** | **verifier subagent 在全新上下文验证** | 隔离实现假设 | 4.3 盲审 | 验证者只看 spec 和验收标准，**不看实现** |
| **Test** | **continuous evals 测 agent 配置，不是产品** | 防止模型/提示升级导致行为漂移 | 4.4 持续 eval | 补充：eval 集要包含**已知失效模式** |
| **Deploy** | **分层 agentic PR review**；人工审查只留给受监管/关键代码 | 审查资源分配 | 6.2 L0~L3 分级 | 给出**按爆炸半径分级**的明确规则 |
| **Deploy** | **approval hooks 作为审批门**；人工暂停放在 Deploy 而非 Build | 不再用人工停顿阻塞 Build | 4.6 硬闸门 | 补充**可逆性**：flag、灰度、影子流量、一键回滚 |
| **Maintain** | **确定性控制带**（Western Electric 规则、σ 分级）；模型不参与检测；2σ 只读诊断，3σ 门控提案 + 回滚 | 避免用模型判断模型 | 4.4 论证走链 + 4.5 可逆性 | 补充"看不懂清单"作为**人类理解**的兜底 |
| **Maintain** | 越界诊断 → 新的 `intent.md`，闭环 | 防止补丁式修复侵蚀架构 | 6.4 契约评审前置 | 补充**保护核心模块变更频率**，防"改散" |

### 3.4 术语统一表

|---|---|---|

### 3.5 Playbook 的四个缺口，本手册补什么

第三方批评和原文自身的留白，集中在四点：

**缺口 1：需求工程太薄。**
`intent.md` 是短文档，`spec.md` 是散文式，假设单一 stakeholder，没有分析步骤，非功能需求藏在 skills 里，可追溯性退化成 git 时间戳。规范一旦错，AI 每小时产出 5000 行错代码。

→ **本手册补**：附录 A 强制每条验收标准配"输入 / 期望行为 / 可观测证据"三列表；没有对应证据的需求视为未定义。

**缺口 2：缺 measurement 层。**
每个 play 都要求指标，但跨六个互不相关的数据源、还要有基线才能定控制带——多数团队做不到。

→ **本手册补**：第 7.3 节给出最小度量集（决策点数量、无人理解模块占比、回滚率、AI 代码事故占比），只要求能从 git 和 CI 读出来的指标，不要求先建完整可观测体系。

**缺口 3：没有变更分级。**
它假设所有变更走同一条流水线，但改一个按钮和改支付逻辑的爆炸半径差几个数量级。同一套流程要么让小改动太重，要么让大改动太轻。

→ **本手册补**：附录 D 的 L0~L3 分级，判级规则"就高不就低"，流程强度随爆炸半径递增。

**缺口 4：保证产物链完整，但不保证有人真的理解产物。**
Git 里每个阶段的工件都在，不等于有人能回答"这个模块坏了会怎样"。

→ **本手册补**：第 5.6 节上线前人类理解审计、附录 E 三问清单、持续维护的"看不懂清单"。

### 3.6 组合使用：骨架 + 信任

```
Anthropic playbook 提供：        本手册提供：
┌─────────────────────┐        ┌─────────────────────┐
│ 六阶段闭环            │        │ 六条基础机制          │
│ 十二个 play           │   +    │ L0~L3 变更分级        │
│ Git 产物链            │        │ 范围守卫              │
│ skills / hooks 分工   │        │ 理解审计 / 看不懂清单  │
└─────────────────────┘        └─────────────────────┘
              ↓                            ↓
        流程跑得起来                每个产物有人负责
```

实践中的分工：

- **用 playbook 定流程**：六个阶段、每个阶段一个产物、Maintain 写回新的 intent。
- **用本手册定判断**：每个产物由谁签字、签什么、证据是什么、出错怎么回滚。
- **用 L0~L3 定强度**：不是每个变更都走完整六阶段；机械变更直接过 CI，高风险变更升到双签 + 影子验证。
- **用理解审计定底线**：上线前必须有人能回答三个问题，答不上来的模块进清单。

## 4. 六条基础机制

### 4.1 审查单位从"代码行"改成"决策点"

一段 3000 行的机械重构可能零决策；一段 30 行的改动可能有三个关键决策（默认值选什么、失败时抛错还是重试、要不要加缓存）。

**按行数分配审查精力是错的，按决策点分配才对。**

每个变更必须带一张**变更意图卡**（模板见附录 C）：人类 5 分钟能读完，签的是判断，不是"我读完了"。

### 4.2 范围守卫：干掉"顺手多做"

"夹杂着看不懂的功能"的主要来源是 AI 的顺手多做——防御性分支、没人要的抽象、兼容层、未启用的配置项。这些东西没人要、没人审、没人维护，最后变成"看不懂的功能"。

纪律：

- **diff 只含意图内的改动，范围外的单独提。**
- 机器可查：文件白名单、行数上限、新增依赖必须人类批准。
- **依赖是最大的不可读来源**，一个没见过的库就能让整段代码失效。

这比事后 review 有效得多，因为它把问题消灭在产生之前。

### 4.3 独立验证，不共享假设

同一个模型写的实现和测试，可以联合自洽地错（common-mode failure，共同模式失效）。必须引入**不共享假设的验证路径**：

- **盲审**：验证者只看 spec 和验收标准，不看实现。人或另一个异构模型都行，能补一部分共同模式失效。**最终签字必须是人。**
- **黑盒验证**：真实数据、真实场景、失败注入、property-based testing、fuzz。
- **关键一问**："什么情况下这个功能一定是坏的？"答不出来，说明没人真正理解它。
- **回归资产**：每个 bug 修复必须留下能复现它的用例，且来源必须是人类可确认的现象（线上问题、用户投诉），不是 AI 猜的。

### 4.4 论证走链条，不走代码

代码只能证明"实现了什么"，永远无法证明"符合需求"。论证必须是这条链：

```
需求 → 验收标准 → 观测证据（测试报告 / 灰度指标 / 用户行为数据）
```

再加一层：**已知失效模式清单 + 缓解措施**。这一层最能建立信任，因为它证明写的人认真想过"怎么会坏"。

AI 参与的功能要做**持续 eval** 而不只是一次性测试，因为模型或提示一变更，行为就会漂移。

### 4.5 用可逆性给"看不懂"封顶

软件和航空最大的不同：**软件能回滚**。

Feature flag、灰度、影子流量、限流、一键回滚——这些让人类不需要 100% 确定也能上线。

反过来，**不可逆的操作**（数据迁移、删除、支付、权限变更）必须升级到最高审查级别，因为那里的"看不懂"代价没有上限。

### 4.6 约束优于审查

与其事后审查 5000 行，不如事前限死 200 行：

- **人类定义稳定层**：分层、模块边界、依赖方向、接口契约。AI 只在模块内实现。人只需要理解边界，不需要理解每个实现。
- **CLAUDE.md 写死项目范式** + 少量范例代码，让 AI 产出"和周围一样"的代码。**可读性来自一致性，不来自漂亮。**
- **小步交付是硬纪律**，因为它是唯一能让审查带宽跟上的办法。
- **依赖白名单**：白名单外的新依赖必须人类批准。
- **能自动判定的交给 hook，不能自动判定的才交给人**：让人类去看自动化能判定的东西，是浪费人类带宽；让自动化去判定价值判断，是制造虚假安全感。

## 5. 首版（0→1）怎么跑

### 5.1 目标定调

首版的核心矛盾是：不确定性最大，但它是**唯一能低成本定架构的窗口**。首版写歪了，后面全是还债。

所以首版的正确目标不是"快点写完"，而是：

> **趁代码还读得懂，把边界和证据链焊死。代码本身反而是最容易重写的部分。**

首版最大的风险不是写错，是**写多了**。AI 会过度实现——功能越少，人类越能理解，后续越好改。

### 5.2 阶段 0：定义成功（人做，1~2 小时）

**Playbook 对应：Plan（`intent.md`）+ Design 的起点。**

一页纸，不超过 2 页（模板见附录 A）：

- 用户是谁
- 三个核心场景
- 不做什么（明确排除）
- 每个场景的验收标准（输入 → 期望行为 → 可观测证据）

这是全项目唯一不能由 AI 代笔的东西。AI 可以追问、补漏、帮你发现矛盾，但**判断必须是人**。

**产物**：`SPEC.md`

**卡点**：spec 人签字。

### 5.3 阶段 1：焊死骨架（人决策 + AI 提供选项）

**Playbook 对应：Design（`spec.md` + 组织 skills）。**

这是首版最重要的一步，也是 AI 最容易越权的地方：

- **技术栈**：AI 给 2~3 套方案和代价对比，人选。
- **目录结构 / 模块边界**：人定，AI 不许自创模块。
- **数据模型**：人定，这是最难改的东西。
- **依赖白名单**：明确列出允许的库。白名单外的新依赖，必须人批准。

**产物**：`CLAUDE.md`（项目宪法：边界、范式、命名、禁止事项、依赖白名单）+ `ARCHITECTURE.md`（一张边界图）。

**卡点**：边界图人签字。

关键：**边界一旦定了，AI 只能在这个盒子里写代码。** 这条规则守住，后面 80% 的不可读问题就没了。

### 5.4 阶段 2：垂直切片，一次一条

**Playbook 对应：Build（`plan.md` + plan mode + diff）。**

**绝对不要横切**（先写所有 model → 再写所有 API → 再写所有 UI）。那是 AI 一次性生成几千行、没人能审的典型死法。

改成**一条用户场景一条垂直切片**：数据 → 业务 → 接口 → UI → 测试，打通一条再下一条。

每条切片的节奏（一条控制在 200~500 行 diff）：

1. **人写变更意图卡**（10 分钟，模板见附录 C）
2. **AI 在 plan mode 出计划**，人看计划、改计划——这一步拦住 60% 的偏差。原则同 playbook：**没有批准的计划，不写实现。**
3. **AI 实现 + 自测**
4. **独立验证**：开一个不带实现上下文的 subagent，只给它 spec 和测试，跑一遍验收
5. **人看意图卡 + 证据签字合并**——不看 500 行代码，看决策和证据

**卡点**：独立验证通过。

### 5.5 阶段 3：证据链当天建（不能等）

**Playbook 对应：Test（失败测试先行 + verifier + evals）。**

首版第一天就要建，因为**后面所有增删改都靠它兜底**：

- CI 从第一天跑：类型检查、lint、单测、契约测试、安全扫描。
- **每条验收标准必须有一条自动化用例对应。没有用例的验收标准 = 未完成。**
- 一条"黄金路径"冒烟测试：3~5 条核心场景端到端跑通。
- 回归用例必须来自人类可确认的现象，不允许"AI 觉得这里该测一下"生成的空转测试。

这一步在首版投入产出比最高。

### 5.6 阶段 4：上线前的"人类理解审计"

**Playbook 对应：Deploy 之前的一道人工闸门。**

首版规模还小，这是**最后一次**能让人真正理解全部代码的机会。

做法：

1. 让 AI 生成**模块地图**（每个模块干什么、依赖谁、被谁依赖、风险点）。
2. 人逐个模块问三个问题：
   - 这个模块坏了，用户会看到什么？
   - 它最可能怎么坏？
   - 出问题怎么降级 / 回滚？
3. 答不上来的模块 → 进**看不懂清单**，要么补测试、要么降权（不碰钱/权限/不可逆操作）、要么重写。

**产物**：`RISK_MAP.md` + 看不懂清单。

**卡点**：每个模块有人能回答三问。

### 5.7 首版交付标准

> 功能跑通 + 每条验收有证据 + 每个模块有人能回答那三个问题。

## 6. 迭代（1→N）怎么跑

### 6.1 目标定调

**Playbook 对应：Maintain → 新的 `intent.md` 闭环。**

首版存的钱，现在开始取。到了这个阶段，代码量必然超过人类阅读带宽，**信任必须靠机制，不能再靠理解**。

重心从"定架构"转向**守边界 + 控爆炸半径**。

1→N 最大的风险不是改错，是**改散了**。AI 让"哪里都能改"变成常态，架构会被一点点侵蚀。

### 6.2 变更分级

| 级别 | 典型变更 | 流程 | 卡点 |
|---|---|---|---|
| **L0 机械** | 格式化、改名、依赖升级、批量替换 | AI 全自动 + CI 兜底 + 抽检。人只确认 diff 无"顺手多做" | CI 绿 |
| **L1 局部** | 单模块内、可回滚的增删改 | 意图卡 → plan → 实现 → 独立验证 → 一人签字 | 回归用例存在 |
| **L2 跨模块** | 改接口、改数据模型、加新模块 | 加一道**契约评审**：先定新接口，人批准后再实现 | 契约测试过 |
| **L3 高风险** | 钱、权限、数据迁移、不可逆操作 | 必须有人**真正读懂实现**，双签 + 影子流量 + 回滚预案 | 影子验证通过 |

判级规则：**就高不就低**。拿不准时，往上一级走。

Playbook 的六阶段是流程模板，L0~L3 决定**这个变更要走多重的流程**——两者是正交的。

### 6.3 三类变更的特殊纪律

#### 新增功能 —— 先问"能不能不加"

AI 让"加功能"的成本趋近于零，导致功能膨胀，这是不可读的头号来源。

新功能必须回答：

- 它属于哪个已有模块？
- 如果不属于，为什么不能复用？
- **新模块 = 新边界 = 人类要重新理解一块东西，成本极高。**

新依赖必须人批准。

#### 删除功能 —— 最安全也最容易做过头

流程：

1. feature flag 关掉
2. 观测一段时间无调用
3. 再删代码

删之前用人可验证的方式（静态分析、日志）确认没有隐藏调用方，**不靠 AI 猜**。

#### 修改功能 —— 最难，最容易出回归

纪律：

> **先写一个能复现旧行为的用例，再让 AI 改到新行为通过。**

这是唯一能证明"只改了想改的"的办法。AI 改 A 的时候很容易顺手重构 B，必须范围守卫。

### 6.4 三条持续机制

1. **契约评审前置**：任何接口/数据模型变更，先改契约定义、人批准，再让 AI 写实现。**契约是唯一人类必须读全的东西**——因为它是边界，不是实现。
2. **保护核心模块的变更频率**：如果某个核心模块每周都被改，说明设计坏了。要主动限制核心路径的改动。
3. **定期清"看不懂清单"**：每季度列出无人能解释实现的模块，处理掉。同时用 eval 集监控 AI 生成功能的漂移——模型或提示一升级，行为可能就悄悄变了。

## 7. 速查表

### 7.1 流程速查

| 本手册阶段 | Playbook 阶段 | 人做什么 | AI 做什么 | 硬卡点 |
|---|---|---|---|---|
| 0→1 定义 | Plan | 写 spec 和验收标准 | 追问、补漏、找矛盾 | spec 人签字 |
| 0→1 骨架 | Design | 定栈、边界、依赖 | 给方案和代价对比 | 边界图人签字 |
| 0→1 切片 | Build | 写意图卡、签计划 | 计划 + 实现 + 自测 | 独立验证通过 |
| 0→1 证据 | Test | 确认用例来源 | 生成测试、跑 evals | 每条验收有证据 |
| 0→1 收尾 | Deploy 前 | 理解审计、风险图 | 生成模块地图 | 每模块能答三问 |
| 1→N L0 | Maintain | 抽检 | 全自动 | CI 绿 |
| 1→N L1 | Maintain | 意图卡 + 签字 | 实现 | 回归用例存在 |
| 1→N L2 | Maintain | 契约评审 | 实现 + 迁移方案 | 契约测试过 |
| 1→N L3 | Maintain | 逐行理解 + 双签 | 实现（从简） | 影子验证通过 |

### 7.2 每次变更前的自检

- [ ] 这张意图卡人类能在 5 分钟内读完吗？
- [ ] 关键决策列出来了吗？每条有"选了什么 / 为什么 / 备选"吗？
- [ ] 明确写了"不做什么"吗？
- [ ] 每条验收标准有对应的自动化用例吗？
- [ ] 验证者是否**没有**看到实现（盲审）？
- [ ] diff 里有没有意图外的改动？
- [ ] 有没有引入白名单外的新依赖？
- [ ] "什么情况下这个功能一定是坏的"能回答吗？
- [ ] 回滚方案是什么？
- [ ] 这个变更属于哪个级别？流程对得上吗？

### 7.3 组织层面三件事

- **新角色：AI 产物审查者。** 职责不是读代码，而是设计验证方案、制定验收标准、维护风险清单。
- **换度量。** 不度量"生成了多少代码"，度量：每个变更的决策点数量、无人能解释的模块占比、回滚率、事故中 AI 生成代码的占比。这四个指标都能从 git 和 CI 读出来，不需要先建完整可观测体系。
- **建立"看不懂清单"。** 列出没有人类能解释其实现的模块。每个要么补证据，要么降权限（不碰钱、不碰用户数据、不碰不可逆操作），要么重写。同时让"我看不懂"能够大声说出来且有人响应——**最危险的不是看不懂，是看不懂但不敢说**。

## 9. 渐进落地路线

Playbook 有六个 play 零前置条件（`intent.md`、plan mode、`CLAUDE.md`、skills、失败测试反馈环、approval hooks），可以直接开始。建议分三波：

### 第一波（第 1 周）：建立最小闭环

1. 意图卡模板（`intent.md` 的人类可读版）+ Plan 阶段的人工签字（附录 C）
2. plan mode 作为默认：没有批准的计划不写实现
3. `CLAUDE.md` 写项目宪法 + 依赖白名单（附录 B）
4. 把验收标准模板用起来（附录 A）
5. CI 跑起来：测试、类型检查、lint

**验收**：完成一次完整的"意图卡 → 计划 → 实现 → 独立验证 → 签字"。

### 第二波（第 2~4 周）：加确定性约束

1. skills 固化切片流程和意图卡模板
2. hooks 把 must-hold 规则变成硬闸门（改核心目录、加依赖、动数据模型）
3. verifier subagent 盲审进流程
4. 引入 L0~L3 分级（附录 D）
5. 建立"看不懂清单"，首次理解审计（附录 E）

**验收**：任意一次变更，能说清它属于哪级、走了哪些卡点、证据在哪。

### 第三波（第 2~3 个月）：闭环与度量

1. 持续 eval 集（含已知失效模式）
2. 灰度 / feature flag / 回滚演练
3. 最小度量集上线（决策点数量、看不懂模块占比、回滚率、AI 代码事故占比）
4. Maintain 阶段接入：异常诊断写回新的意图卡
5. 每季度清一次"看不懂清单"

**验收**：能从 git 和 CI 回答"这个功能凭什么可信"。

## 10. 收尾

- **首版：用"还能理解"换"结构"** —— 趁读得懂，把边界和证据链焊死。
- **1→N：用"结构"换"不必理解"** —— 靠边界、契约、证据、可逆性，让人不必读懂每一行也能负责。

首版最大的风险不是写错，是**写多了**；1→N 最大的风险不是改错，是**改散了**。

这两条，AI 恰好都会推着你往坏的方向走——所以纪律必须是硬的。

## 附录 D：变更分级定义

> Playbook 没有变更分级；这是本手册的补充，用来决定一个变更走多重的流程。

| 级别 | 判定标准 | 例子 | 审查强度 |
|---|---|---|---|
| **L0** | 不改变任何行为，纯机械 | 格式化、改名、依赖小版本升级 | 全自动 + 抽检 |
| **L1** | 改变行为，但局限于单模块，且可回滚 | 单页面功能、单接口字段 | 一人签字 + 自动化 |
| **L2** | 跨模块，或改变接口 / 数据模型 | 新增服务、改 API 契约、加表 | 契约评审 + 两人 |
| **L3** | 爆炸半径无上限，或不可逆 | 支付、权限、数据迁移、删除 | 逐行理解 + 双签 + 影子验证 |

判级规则：**就高不就低**。拿不准时，往上一级走。

## 附录 E：人类理解审计清单

> Playbook 保证产物链完整，但不保证有人理解产物；这份清单补的是后者。

对每个模块逐项确认：

- [ ] 这个模块的职责能用一句话说清吗？
- [ ] 它依赖谁、被谁依赖，画得出来吗？
- [ ] 它坏了，用户会看到什么？
- [ ] 它最可能怎么坏？（列出至少 2 个失效模式）
- [ ] 有没有对应的测试能捕捉这些失效？
- [ ] 出问题怎么降级 / 回滚？
- [ ] 如果答案有"不知道"，它是否在处理钱 / 权限 / 不可逆操作？

处理方式：

- 不碰敏感路径 → 补测试、写意图文档，继续观察。
- 碰敏感路径 → **立即降权**（下线、加人工确认、换成熟方案）。
- 完全无法理解且无法补证据 → **重写**成人类能懂的形式。
